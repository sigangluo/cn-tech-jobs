# 故障手册

规则见 [CLAUDE.md](CLAUDE.md)，已知可接受的异常见 [known-issues.md](known-issues.md)。
原则：**宁可中止也不发布半截数据；不要为了让脚本变绿而放宽校验**（容忍度、阈值）。放宽前先弄清它为什么触发。

## 抓取失败

`update.py` 已自动重试过一次，仍失败的公司标「失败」并给出最后几行错误：

| 错误特征 | 多半是 | 怎么办 |
|---|---|---|
| `ConnectionError` / `RemoteDisconnected` / `Timeout`，单家且很快失败 | 瞬时网络问题 | 隔几分钟 `update.py --only <key>`，再 `--build-only`。反复出现是站点对本机 IP 不友好，别硬改代码 |
| `一直被限流`，或耗时表「限流次」≠ 0 | 请求太密 | 调大该站 `DELAY` 或调小并发（腾讯 `WORKERS`、阿里 `BG_WORKERS`），**不要**加并发 |
| `官网共 N 条，只抓到 M 条` | 翻页漏项 / 翻页期间大量变动 | 先重跑；稳定复现说明翻页有上限或会漏，按条件拆分抓取（参考 `companies/bytedance` 的城市拆分）。**不要**调大 `ensure_complete` 容忍度 |
| `KeyError` / `TypeError` / `接口返回异常` / 返回非 JSON 或空 | 接口改版，或被反爬 | 浏览器 F12 看官网现在的请求和返回，对照 `fetch.py` 改；站点在维护就等 |
| `看板类别 [...] 一条都没抓到` | 类别名变了 | 按错误里列出的「抓到的类别」更新 `META["categories"]` |

修不好又急着发布：**不要**拿旧 CSV 冒充新数据。等，或告诉用户这家本周缺失（页脚逐家显示最近成功抓取时间，旧数据会如实标日期）。

## 数量骤降（质量门槛拒绝覆盖）

提示「职位数减少超过 30%（技术 100 -> 40）」，旧 CSV 未被覆盖。

1. `update.py --only <key>` 重跑一次排除偶发。
2. 对照官网：打开 `META["list_url"]`，看官网自己显示的职位总数。
3. 官网也大幅减少 → 真下架，`--accept-large-drop <key>` 并在汇报里写明；官网没变、我们抓得少 → 抓不全，按上一节处理，**不要**接受。接受会让下一份报告以新数量为基准，所以必须有依据。

## 质量报告 alerts

alerts 按 `scripts/audit.py` 的 `THRESHOLDS` 生成，是复核队列不是错误。已在 known-issues 且没明显恶化的忽略；**新出现的**先看 `reports/<日期>.json` 该公司的 `samples`（固定抽样，含原文），判断是官网数据本身如此还是我们解析出了问题：

- 「没识别出工作年限」突然升高：官网任职要求写法变了？抽原文看，必要时改 `lib/years.py` 并补测试。
- 「缺直达链接 / 缺城市」突然升高：官网字段改名了？
- 「年限来源未记录」≠ 0：抓取脚本没走 `resolve_years`。
- 「职位数比上次少」：见上一节。

确认是官网本身如此且长期存在的，补进 known-issues；不要为让 alert 消失去调阈值。

## 变慢了

总耗时 ≈ 最慢那家（公司并行），看耗时表判断，别凭感觉。**基线（2026-11-07，随官网变化，仅供对照）**：整次约 7 分钟；腾讯约 7 分钟（1457 次请求，逐条取详情）、阿里约 5 分钟、蚂蚁和字节约 4–5 分钟、其余 2 分钟内；全部公司限流次数为 0。

- 瓶颈是**单次请求延迟，不是限流**（字节 64 次请求 252 秒、等待 0 秒），所以提速靠并行，不是调退避。「限流次」变成非 0 说明并发过高，调回去。
- 「等待s」占大头：在被限流或反复重试，先查为什么失败。
- 已做的提速：阿里事业群站点并行（740s → 295s）、腾讯详情并发 5 → 8（620s → 428s）。再提速的选项是缓存腾讯没变的职位详情（按 PostId + 更新时间），但要新增本地状态文件，总耗时不到不可接受就不值得。

## 类别误收 / 漏收

先看 `reports/<日期>.json` 的 `inferred_category` 样本，判断是个别还是一类。按「一类职位」改规则（位置见 CLAUDE.md「类别推断」），在 `tests/test_scope.py` 补正反用例，再 `update.py --build-only` 对比前后数量。官网明确给了类别的职位不受这些规则影响。

## 发布出问题，回滚

```bash
ls -t .backups/
python3 scripts/publish.py --archive .backups/<上一份>          # 先检查
python3 scripts/publish.py --archive .backups/<上一份> --push   # 用户确认后
```

`.backups/` 只在本机；换机器后只能重新 `update.py` 再发布。

## CI（weekly-audit）失败

Actions 页面：摘要表是质量报告，产物 `quality-report` 含 `quality.json` 和 `update.log`（含耗时表）。本机能抓而 CI 失败，多半是 GitHub 的海外服务器被官网限制，看 `update.log` 是哪家；个别公司在 CI 不可达可接受，但记入 known-issues，不要去改本机流程。全部失败先看依赖是否变了（`requirements.txt` 已锁小版本）。可在 Actions 里手动触发。

## 验证前端改动

`node --check` 两个 js + `node tests/state.test.js`；再 `python3 scripts/serve.py` 在浏览器里验证：筛选联动、搜索（只下载所选公司的 JD）、图表 / 数据表切换、职位详情、复制地址栏链接到新标签页能恢复筛选、深色模式、窄屏。浏览器自动化先征得用户同意。
